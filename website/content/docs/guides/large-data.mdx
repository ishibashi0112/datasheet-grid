グリッドは行・列ともに仮想化されており、DOM 化されるのは可視域 + オーバースキャンぶんだけです。クライアントサイド行モデルで**約 100 万行**まで扱えます。

## デモ(100,000 行)

<LargeDataDemo />

- **ID** 列は左に、**状態** 列は右にピン留めされています(`pinned: 'left' | 'right'`)。横スクロールしても固定されたままです。
- 「50,000 行目へ」ボタンは命令的ハンドルの `scrollToRow(49999, { align: 'center' })` を呼んでいます。
- **在庫金額**列は `getValue` による計算列(数量 × 単価)で、`numberFormatter()` により 3 桁区切り表示です。
- フィルター / ソート / グローバルフィルターも 100,000 行に対してそのまま機能します。

## 列のピン留め

```tsx
const columns: GridColumn<Row>[] = [
  { key: 'id', title: 'ID', width: 90, pinned: 'left' },
  // ...中央スクロール列...
  { key: 'status', title: '状態', width: 100, pinned: 'right' },
]
```

レイアウトは左 / 中央 / 右の 3 ペイン構成(sticky ベース)で、固定列は常に可視です。`scrollToCell` は固定列に対しては横スクロールしません。

固定列(行番号の列を含む)の合計がグリッドより広く、中央に `max(120px, グリッドの幅の 1/4)` を残せない間(スマホの幅など)は、右の固定列の内側から、次に左の固定列の内側から順に、表示の上だけ固定を外して中央でスクロールさせます。`columns` の `pinned` は変えず、グリッドが広くなれば固定に戻ります。

## 大きなデータでの注意点

- `rows` は**参照の安定**が重要です。`onRowsChange` で受け取った配列はそのまま state に戻してください(map で作り直すと未変更行の構造共有が失われ、undo 履歴も破棄されます)。
- ソート中に 1 セルを編集したり、末尾に行を足したりしても、全行を並べ直すことはしません。ソート列の値が変わった行と足した行だけを新しい位置へ差し込み直し、ソート列と無関係な編集では並びをそのまま使います(列フィルターも、絞り込み結果が変わらなければ前回の結果を使います)。一度に多くの行(1,024 行超)のソート列が変わったとき・足したとき、末尾以外に足したときは全件ソートします。
- 論理全高(行数 × 行の高さ)が 15,000,000px(36px の行で約 41 万行)を超えると、ブラウザの要素の高さの上限に収めるため、スクロールの位置を縮めて写します。行を足したり減らしたりしても、見ている行はそのままです(1.0.1 から)。この範囲では展開行(`detailRow`)は描かず、トグルも出しません。
- グローバルテキストフィルターは 50,000 行を超えると自動的に**時間分割適用**へ切り替わり、入力中もメインスレッドをブロックしません(適用中はグリッドが組み込みオーバーレイを表示)。
- 一方、全行の並べ替え(ソート)、列フィルターの適用(dateSet の相対プリセットを含む)、CSV の書き出し(`downloadCsv` / `exportCsv`)は時間分割しません。100 万行では文字列の列のソートや「今日」のプリセットで約 1〜2 秒、`downloadCsv` で約 5 秒、画面が止まります(進み具合の表示は出ません。手元の計測)。この規模で頻繁に使う場合は、書き出しの前に「書き出し中…」を自分で表示する、[サーバーサイド行モデル(SSRM)](/docs/guides/ssrm)でサーバーに並べ替え・絞り込みを任せる、などを検討してください。
- 行の可変高(`autoHeight`)は計測コストが増えるため、超大規模データでは固定行高を推奨します。
- データがサーバにある場合は[サーバーサイド行モデル(SSRM)](/docs/guides/ssrm)を使うと、可視域近傍のブロックだけを取得してメモリを有界化できます。
